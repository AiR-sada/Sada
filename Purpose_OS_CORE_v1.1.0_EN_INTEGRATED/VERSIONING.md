# VERSIONING.md

この文書は Purpose OS — CORE の版管理方針を定めます。
本文書は非規範ですが、公開運用の実務基準として用います。

規範的な内容の正本は常に `spec.md` です。矛盾がある場合は `spec.md` が優先します。

---

## 基本方針

- 版番号は Semantic Versioning の考え方に沿って、`MAJOR.MINOR.PATCH` を用います。
- 一度公開した版は書き換えません。
- 内容変更は、常に新しい版として公開します。
- `v1.1.0` は **public API の定義点** であり、以降の版は本方針に従って積み上げます。
- official lineage・継承・fork・Purpose 改訂・退役の運用は `GOVERNANCE.md` を参照します。

## この仕様の public API

この仕様における参照互換性の中核は、次を含みます。これらは版をまたいで引用・参照される対象として扱われます。

- `spec.md` が唯一の正本であること
- 文書タイトル（`Purpose OS — CORE`）
- version
- 章構成（序 / CORE 第1部 / CORE 第2部 / 参照部）
- 概念ID（例: `序-2 Purpose`, `①-8 現実(i)`, `②-9 意思決定`, `参-1 構造`）
- 各ミクロの `依存` 行
- 規範 / 非規範 の境界

## MAJOR

次のいずれかに当たる変更は MAJOR です。

**ただし、Purpose 自体の改訂は MAJOR ではなく `ROOT-MAJOR` として扱います。**

- 既存概念の意味を壊す変更
- 概念IDの変更・削除・再割当て
- 章構成の互換性破壊
- `依存` 行の変更による意味上の互換性破壊
- 正本優先ルールや規範境界の破壊的変更
- 後続モジュールが CORE の意味を変更するような破壊的拡張

例:

- `①-8 現実(i)` の意味を別物に変える
- `②-9 意思決定` の依存関係を破壊的に変更する
- `spec.md` 以外を正本に昇格させる
- `序`・`参照部` の章構成を入れ替える

## ROOT-MAJOR（特別な MAJOR）

次のいずれかに当たる変更は ROOT-MAJOR です。

- `序-2 Purpose` の定義内容そのものを変更する
- Purpose の構成要素・基本方向・根本表現を改訂する
- その版で採用される規範上の唯一の起点の内容を差し替える

ROOT-MAJOR の運用ルール:

- ROOT-MAJOR の提案は誰でもできる
- official lineage への採用判断は、current steward または正当に handoff された successor が `GOVERNANCE.md` に従って行う
- `GOVERNANCE.md` に定める公開記録を要する
- 改訂理由・旧Purposeとの差分・なぜより良いと判断したかを残す
- 提案には `release/ROOT_MAJOR_TEMPLATE.md` の利用を推奨する
- 旧版は削除せず、少なくとも `superseded` として残す

## MINOR

既存意味を壊さず、後方参照互換を保った追加は MINOR です。

- 新しい概念の追加（既存IDは動かさない）
- CORE に依存する新しい後続モジュールの追加
- 既存意味を変えない補足的な非規範文書の追加
- 既存意味を変えない翻訳版・機械可読版の追加
- 補助注記・非規範の例の追加

例:

- CORE に依存する新モジュール（例: 検証、衝突解決）の追加
- 英語要約の追加
- AI・successor 向け補助文書の追加
- 機械可読な補助表現（JSON-LD 等、非規範）の追加

## PATCH

意味を変えない修正は PATCH です。

- 誤字脱字の修正
- 表記揺れの修正
- レイアウト修正
- 参照先の見た目の整備
- 非意味変更の補助文書更新

PATCH は、意味・概念ID・依存・章構成・正本性を変更しません。

## 退役と置換

公開済みの概念・識別子・文書は、原則として **静かに消去しません**。
必要な場合は、次の状態で扱います。

- **deprecated**: まだ参照可能だが、新規採用は推奨しない
- **superseded**: 別の概念・文書・module に置き換えられた
- **withdrawn**: 公開記録は残すが、採用対象から外す

運用ルール:

- 概念IDは **再利用しない**
- 退役時は tombstone（旧識別子・状態・置換先・退役版の最小記録）を残す
- `superseded` では置換先を明記する
- 退役の詳細運用は `GOVERNANCE.md` に従う

## 公開運用

### 凍結の原則

- 公開済みの `v1.1.0` は凍結します。
- 問題が見つかっても、既存公開物は上書きしません。
- 修正は `v1.0.1` 以上、または必要に応じて `v1.1.0` / `v2.0.0` として出します。

### GitHub immutable releases の使用

本リリースは GitHub の **immutable releases** 機能を用いて凍結する前提で設計されています。

- リポジトリ設定で immutable releases を有効化してから公開します。
- 公開後は release assets と関連 Git tag を変更・削除できません。
- 具体的な手順は `release/PUBLISH.md` を参照してください。

### ドラフト経由の公開

immutable release を公開する際は、以下の順で行います。

1. リポジトリ設定で immutable releases を有効化する。
2. release を **draft** として作成する。
3. 全ての関連 assets を draft に揃える。
4. 内容を最終確認する。
5. draft を publish する。この時点で tag と assets は凍結されます。

draft 段階では修正可能ですが、publish 後は assets と tag を修正できません。

### 外部アーカイブとの関係

外部アーカイブ（Zenodo 等）で DOI を取得する場合は、次のいずれかを選択します。

- **先行予約方式**: Zenodo で DOI を事前予約し、その DOI を `spec.md` の frontmatter と `CITATION.cff` に記載してから、GitHub と Zenodo の両方で公開する。この場合、予約 DOI は draft 削除で失われる点に注意。
- **事後付与方式**: GitHub-Zenodo 連携で、GitHub release から Zenodo が自動で DOI を発行する。この場合、spec ファイル内部には DOI は記載されない。

v1.1.0 では外部 DOI は必須ではありません。付与する場合は、選択した方式と記載方針を `release/PUBLISH.md` に従って決定します。

## pre-1.0 の経緯の扱い

v1.1.0 到達までの設計変遷は `CHANGELOG.md` の「v1.1.0 到達までの主要な設計判断」に要約として記載します。これは非規範の記録であり、v1.1.0 より前のバージョン番号（v0.x 等）は公開物として存在しません。
